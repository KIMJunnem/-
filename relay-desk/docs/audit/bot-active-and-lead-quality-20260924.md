## 1. 지금 켜진 요청봇

**근거 1. 확장 파일** — soomgo-bot-extension/manifest.json

- version: `0.4.21`
- content_scripts: `automation-guard.js`, `content-v3.js`, 두 개뿐이다. `content.js`·`content-v2.js`·`content.v1.backup.js`는 폴더에만 있고 manifest가 부르지 않는다.
- 발행본 dist/downloads/relay-desk-soomgo-bot/manifest.json은 원본과 바이트 단위로 같다.

**근거 2. 서버가 받는 심박** — `/api/health` `botHealth.request`와 `/api/state` `botStatus.request`

- version `0.4.21`, 상태 "새 요청 확인 중", 마지막 심박 13:47, 주소 경로 `/requests/received`
- v3는 심박에 `chrome.runtime.getManifest().version`을 실어 보낸다(content-v3.js 207줄). 그래서 이 값은 실제로 불러온 확장의 manifest 버전이다.
- v2 코드에는 심박(`/api/soomgo/bot-status`)을 보내는 부분이 없다.
- `/api/soomgo/bot-version`: 요청봇 0.4.21 · 채팅봇 0.3.23 · 발행 9/24 03:16.

**근거 3. 기록 형식** — soomgoLeads 403건 전체

| 형식 | 마지막 기록 | 9/20 이후 건수 |

**판단**

- 숨고 요청 페이지에 붙는 것은 v3다. v2가 숨고 페이지에서 켜져 있다면 요청을 열 때마다 v2 형식 기록이 남아야 하는데, 9/19 이후 0건이다.
- **남는 경우 하나:** 예전에 불러온 다른 폴더의 확장이 꺼진 채 설치만 돼 있을 수 있다. 이건 파일과 기록으로는 볼 수 없다.

  - **준희 확인:** chrome://extensions에 "Relay Desk · 숨고 자동 견적"이 몇 개 있는지, 각각 어느 폴더에서 불러왔는지.

## 2. v2 끄는 방법 (수정안, 적용은 준희 승인 뒤)

지금 v2가 활성은 아니다. 그래도 다시 살아나지 못하게 막는 예방책이다.

**수정안 1. 서버가 v2 요청을 거절**

- 위치: server/relay-server.js `/api/soomgo/quote` 시작 부분(7962~7968줄, 빈 요청 거절 바로 뒤)
- 거절 조건: 헤더 `x-relay-bot`이 `soomgo-extension-v2`이거나 요청번호가 `-quote-\d{13}$`로 끝나면 `410 { error: 'retired_bot_version' }`을 돌려준다. 기록은 남기지 않는다.
- 효과: v2는 응답이 오류면 견적을 넣지 않고 스스로 꺼진다(content-v2.js runDetail의 catch → `state.on=false`). 그래서 옛 v2가 다시 켜져도 "보내기"까지 가지 못한다.
- 시험: tests/soomgo-quote-extension-stage2-4-1.cjs 또는 새 시험에 "v2 헤더 → 410·lead 0" 한 줄을 넣는다.
- 되돌림: 추가한 몇 줄을 빼거나 백업을 다시 올린다. 재시작하면 원래대로 돌아간다.
- 옛 봇 파일(content-v2.js·content.js·content.v1.backup.js)을 폴더에서 backups/로 옮기는 것은 파일 이동이다. 준희 허락을 받고 한다. manifest가 쓰지 않으므로 옮기지 않아도 동작은 같다.

## 3. 기록 품질 수정안

**지금 soomgoLeads 403건 구성**

| 종류 | 건수 | 비고 |
|---|---|---|
| 숨고 요청번호형(받은 요청 주소) | 276 | 서로 다른 요청번호 276개 |
| 채팅방 화면을 요청으로 읽음(`PAGE-`) | 66 | 채팅방 65, 그 밖 1. 모두 9/16·9/19 |
| v2 재계산(같은 요청 1건) | 14 | 그 요청은 요청번호형으로도 이미 기록돼 있어 14건 모두 중복 |
| 시험·진단 기록(SELFTEST·TEST·PRICE·DIAG 등) | 36 | 출처가 "Soomgo"로 적혀 있어 통계에 섞인다 |
| `SOOMGO-지문` | 9 | 요청번호 없이 들어온 것. 9/16·9/18. 실제 요청인지 모름 |
| 요청번호를 잘못 읽은 것(`request_detail`, `received`) | 2 | 옛 봇 [추정] |

실제로 서로 다른 숨고 요청은 **약 276건(최대 285건)**이다. 기록 403건의 68~71%다.

**수정안 2. 채팅방 주소는 요청으로 기록하지 않음**

- 위치: relay-server.js `/api/soomgo/quote` 시작 부분(수정안 1과 같은 곳)
- 조건: 요청번호가 `PAGE-`로 시작하거나 `sourceUrl`이 `/pro/chats/`이면 `422 { error: 'not_request_page' }`를 돌려주고 기록하지 않는다.
- v3는 요청 상세 주소(`/requests/received/<번호>`)에서만 요청을 연다(content-v3.js 85~88줄). 그래서 v3 동작은 달라지지 않는다.

**수정안 3. 같은 요청번호는 한 건으로**

- 위치: 같은 엔드포인트, 요청번호를 정하는 곳(8052줄 부근 `requestId`)
- 요청번호 끝의 `-quote-13자리시각`을 떼어 저장한다.
- 이미 있는 "같은 요청번호면 새로 만들지 않고 기존 lead를 갱신"하는 경로(8055~8083줄)를 그대로 타므로 추가 코드가 거의 없다.
- 시험 기록은 출처를 `Soomgo`가 아니라 `SelfTest`로 적게 한다. 해당 시험들의 입력만 바꾸면 되므로 서버 코드는 손대지 않는다.

**수정안 4. 기존 기록을 통계에서 빼는 읽기용 집계** (데이터는 고치지 않는다)

- 새 스크립트나 기존 깔때기 집계에 같은 규칙을 넣는다. 규칙:
  1. 시험 요청번호(SELFTEST·TEST·PRICE·DIAG·diagnostic·discount·UNIQ·defer-test·scenario 등)는 뺀다.
  2. `PAGE-`는 뺀다.
  3. 요청 키는 받은 요청 주소의 번호로 하고, 없으면 요청번호에서 `-quote-시각`을 뗀 값으로 한다. 같은 키는 한 건으로 센다.
  4. `SOOMGO-지문`은 따로 "모름"으로 센다.
- 기존 funnel-synthetic-filter(tests/funnel-synthetic-filter.cjs)가 쓰는 제외 규칙과 합쳐 한 곳에서 관리한다.
- 이 규칙을 적용하면 9/19 영상편집은 94건이 아니라 서로 다른 요청 약 14건이 된다(지시 13 표).

## 적용 순서 (적용 지시가 나오면)

1. 백업: backups/lead-quality-<날짜>/에 relay-server.js와 해당 시험 파일
2. 샌드박스 전체 시험 → PC 전체 시험(run-all) → 재시작
   - 지금 PC 전체 시험은 채팅봇 manifest 0.3.24 ≠ 0.3.23 때문에 52/78에서 멈춘다. 이것부터 정리해야 한다(13:46 progress 참고).
3. 확인은 샌드박스 시험으로만 한다: v2 헤더 요청 → 410, 채팅방 주소 → 422, `-quote-` 요청번호 → 원래 번호의 lead로 합쳐지는지. PC 서버에 가짜 요청을 보내 확인하지 않는다(실제 기록이 바뀌므로).
