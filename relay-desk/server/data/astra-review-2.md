## Astra 재검수 2/3 — `relay-server.js` 독립 검토 원문

**검토 범위:** 제공된 1~133행 발췌. 표제는 `1-180`이지만 실제 내용은 133행의 상품 정의 중간에서 끝납니다. 따라서 전체 파일의 구문 정상 여부, 카탈로그 전체 항목 수, 후속 구현은 판정하지 않았습니다.

**수행 범위:** 이 채팅에서는 파일 접근·수정·명령 실행을 할 수 없습니다. 아래는 제공된 코드의 정적 검토 결과와 **미적용 수정안**이며, 파일 변경 또는 테스트 완료 보고가 아닙니다.

### 종합 판정

**이 발췌만으로 운영 승인 불가.** 특히 결제 규칙의 모순 가능성, 비용 제한 설정의 숫자 검증 부재, 카탈로그 기준 불일치를 먼저 해소해야 합니다. 프롬프트에 안전 규칙이 적혀 있다는 사실과 실제 서버가 해당 규칙을 강제한다는 사실은 구분해야 합니다.

### 2. [P1 / 확정] 숫자 환경변수 검증이 없어 제한·타이머가 비정상 값이 될 수 있음

**근거: 21, 25, 29, 32~33행**

**문제**

- `Number('abc')`는 `NaN`이며 `Math.max(0, NaN)` 역시 `NaN`입니다.
- 비용 제한이 `NaN`일 때 후속 코드가 `usage >= cap`으로 비교한다면 제한이 작동하지 않을 수 있습니다. 실제 비교 코드는 추가 확인이 필요합니다.
- `Infinity`, 음수 타임아웃, 소수 포트 등을 명시적으로 거부하지 않습니다.
- 타이머에 부적절한 값이 전달되면 의도한 간격과 달리 동작할 수 있습니다.
- 문자열 `'0'`은 truthy이므로 현재 코드도 0을 읽습니다. 문제는 **0의 의미와 허용 범위를 정의하지 않았다는 점**입니다.

**패치 방향 — 공통 파서 제안**

```js
function readNumberEnv(name, fallback, { min, max, integer = false }) {
  const raw = process.env[name];
  const value = raw === undefined ? fallback : Number(raw);

  if (
    (raw !== undefined && raw.trim() === '') ||
    !Number.isFinite(value) ||
    value < min ||
    value > max ||
    (integer && !Number.isInteger(value))
  ) {
    throw new Error(`Invalid numeric configuration: ${name}`);
  }

  return value;
}
```

- 포트·타임아웃·보고 간격·토큰 한도·비용 한도에 각각 범위를 지정합니다.
- 타이머에는 런타임이 지원하는 최대 지연값 이하의 상한을 둡니다.
- 비용 제한의 0은 “호출 금지”인지 “제한 해제”인지 명시합니다. 비용 보호 목적이라면 암묵적인 제한 해제로 사용하지 않는 편이 안전합니다.
- 잘못된 운영 설정은 조용히 보정하기보다 시작 시 실패시키고 오류를 표시합니다.

**필수 검증:** 미설정, 빈 문자열, 공백, `abc`, `NaN`, `Infinity`, 음수, 0, 소수, 상한 초과.

- **16행:** `Set`은 현재 프로세스 안에서만 공유됩니다. 여러 프로세스·인스턴스가 운영된다면 영속적인 작업 선점과 멱등성 제어가 필요합니다. 단일 프로세스에서도 예외 시 `finally`로 잠금을 해제하는지 확인해야 합니다.
- **15행:** 일시정지 파일 존재 확인 자체는 진행 중인 작업 취소를 보장하지 않습니다. 외부 전송·결제 요청 직전에 정지 상태를 다시 확인하고 진행 중 작업의 중단·보류 정책을 정해야 합니다.
