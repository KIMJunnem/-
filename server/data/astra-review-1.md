# Astra 검수 1/3 — 독립 코드 리뷰

- **대상:** 제공된 `server/relay-server.js` 발췌
- **검토 범위:** 1–180줄, 1590–1661줄에 표시된 코드와 문자열
- **검토 방식:** 정적 텍스트 검토
- **수정·실행 여부:** 없음. 이 대화에서는 파일 수정, 명령 실행, 고객 채널 조작, 설정 변경을 할 수 없습니다. 아래 수정 내역은 **적용이 필요한 수정안**이며, 구현 완료 보고가 아닙니다.
- **종합 판정:** **제공된 발췌만으로 자동 결제·최종검수·파일 전달의 안전성을 승인할 수 없습니다.** 확인된 코드 결함과 운영 계약 충돌이 있으며, 핵심 실행 경로의 검증도 필요합니다. 발췌 밖에 보호 장치가 없다고 단정하지는 않습니다.

## 1. 확인된 문제와 수정 필요 내역

### 1) [P0] Astra 통과 판정이 잘못된 점수와 누락된 수정 목록을 허용함

**근거: 155–170줄**

`astraGradeAOrAbove()`는 다음 조건만 검사합니다.

- 상태가 `completed`
- `Number(grade.score) >= 90`
- 결정이 `통과`
- `requiredFixes`가 배열이 아니거나 빈 배열

따라서 이 함수만 보면 다음과 같은 비정상 결과도 통과할 수 있습니다.

- 점수 `101`, `"Infinity"`
- `requiredFixes` 누락
- `requiredFixes: null`
- `requiredFixes: "출처 수정 필요"`

특히 170줄은 **수정 목록이 잘못된 형식이면 거부하는 대신 허용**합니다. 155–162줄에 분야별 배점은 정의되어 있지만, 이 함수에서는 분야별 점수와 총점의 일치도 검사하지 않습니다.

**수정 필요 내역**

- 채점 응답을 엄격한 스키마로 검증합니다.
- 점수는 유한한 숫자이며 `0–100` 범위여야 합니다.
- `requiredFixes`는 필수 배열로 받고, 누락·형식 오류는 검수 보류로 처리합니다.
- 분야별 점수 범위와 총점 합계를 검증합니다.
- 안전 위반·파일 손상·필수 형식 불일치는 총점과 무관하게 납품을 차단합니다.

**검증 기준:** 정상적인 90점 이상 판정만 통과하고, 위 비정상 입력은 모두 거부되어야 합니다.

### 2) [P0·계약 충돌] 결제 후 3시간 경과를 거래 확정·리뷰 요청의 기준으로 삼고 있음

**근거: 40–46줄, 50줄**

50줄은 “새 결제 확인 뒤 추가 작업을 시작”하고, “결제 완료 3시간 후 거래 확정 요청” 및 리뷰 요청을 진행하도록 지시합니다.

하지만 이 조건에는 **실제 작업 완료, 최종검수 통과, 결과 전달, 고객 확인**이 명시되어 있지 않습니다. 이 지시가 그대로 실행되면 작업 중이거나 전달 실패 상태에서도 거래 확정 요청이 나갈 수 있습니다.

**수정 필요 내역**

- 시간 경과만으로 거래 확정·리뷰 요청 상태로 넘어가지 않도록 계약을 변경합니다.
- 착수금 거래와 최종 납품 거래의 확정 조건을 분리합니다.
- 최종 거래는 계약 및 플랫폼 정책에 맞는 납품·확인 조건을 충족한 경우에만 확정 요청 대상으로 삼습니다.
- 분쟁·취소·환불·추가금 협의·전송 불명 상태에서는 자동 요청을 차단합니다.
- 발췌의 플랫폼 관련 설명은 현재 실제 정책과 별도 대조해야 합니다.

### 3) [P0·계약 미비] 추가금 발생 시 기존 결제 취소·재등록의 정산 조건이 불명확함

**근거: 39줄, 48–50줄, 138–149줄**

50줄은 고객의 추가금 동의 후 기존 거래를 취소하고 최종금액으로 새 결제를 등록하도록 지시합니다. 그러나 다음 조건은 발췌된 계약에 구체적으로 정의되어 있지 않습니다.

- 기존 거래 취소·환불이 확인되었는지
- 이미 확정된 착수금이 있는지
- 새 결제액에서 기존 정산액을 어떻게 처리하는지
- 취소 성공 후 새 거래 등록에 실패했을 때 어떤 상태로 남는지

또한 추가금 규칙에는 10,000원이 존재하지만(141–143줄 등), 각 거래는 15,000원 이상이어야 한다고 명시되어 있습니다(50줄). **추가금이 10,000원이라는 것 자체는 결함이 아니지만**, 이를 별도 거래로 요청하면 내부 계약과 충돌합니다.

**수정 필요 내역**

- 동의 대상인 범위·추가금·최종 총액·견적 버전을 함께 저장합니다.
- 취소 요청과 취소 확인, 환불 진행과 환불 확인을 구분합니다.
- 기존 결제·환불·정산액을 대조한 후 재등록 금액을 결정합니다.
- 별도 거래의 최소금액 조건을 검증하되, 조건 충족을 위해 고객 동의 없이 금액을 올리지 않습니다.
- 정산이 불명확하면 추가 결제 요청과 추가 작업을 모두 보류합니다.

### 4) [P1] 고객응대 계약과 실제 상담 안내 문자열이 충돌함

**근거: 47줄, 64줄, 1626–1628줄, 1631–1658줄**

47줄과 64줄은 자연어 응답 허용, 번호 입력 비강제, 한 번에 하나의 질문을 요구합니다.

그러나 `serviceIntakeGuide()`는 다음과 같이 안내합니다.

- “아래도 번호로 답해 주세요.” — 1637줄
- 회사·직무, 문항 수, 글자 수, 경험 자료, 초안을 한 번에 질문 — 1638–1642줄
- 교정·타이핑·번역에서도 번호 응답 요구 — 1646·1651·1656줄

이 함수의 반환값이 고객에게 그대로 사용된다면 운영 계약과 충돌합니다. 실제 호출·발송 여부는 발췌에서 확인할 수 없습니다.

**수정 필요 내역**

- 알려진 정보를 제외하고 다음 미확인 항목 하나만 질문하도록 변경합니다.
- 번호는 선택 가능한 보조 수단으로만 제시합니다.
- “자료가 흩어져 있어 정리 필요(추가금)”은 추가금 확정이 아닌 **범위 확인 후 별도 안내·동의 대상**으로 표현합니다.
- 고객 질문 답변을 정보 수집보다 우선합니다.

### 5) [P1] 서비스 수와 고객 노출 범위의 기준이 서로 다름

**근거: 39줄, 62–63줄, 126–136줄**

39줄과 62줄은 20개 판매 서비스를 기준으로 브랜딩 산출물을 만들도록 지시하지만, 63줄과 실제 카탈로그는 고객용 9개 항목을 기준으로 합니다.

현재 텍스트만으로는 20개가 내부 세부 상품인지, 고객에게 판매하는 별도 서비스인지 구분되지 않습니다. 생성되는 소개문·가격표·제안서가 서로 달라질 수 있습니다.

**수정 필요 내역**

- 고객용 서비스 목록의 단일 기준을 지정합니다.
- 내부 20개 세부 서비스가 필요하다면 고객용 9개 항목과의 대응표를 별도로 정의합니다.
- 서비스 수와 명칭을 여러 프롬프트에 수동 중복 기재하지 않도록 변경합니다.

### 6) [P1] 비용·토큰·타임아웃 설정에 유한성·형식 검증이 없음

**근거: 25줄, 29–33줄**

`Number()`와 `Math.max()`만으로는 안전한 설정 검증이 되지 않습니다.

- 잘못된 문자열은 `NaN`이 됩니다.
- `"Infinity"`는 무한대가 됩니다.
- 음수 비용 한도는 조용히 `0`으로 바뀝니다.
- 타임아웃은 0·음수·비정상 값도 받을 수 있습니다.
- `0` 한도가 “사용 금지”인지 “무제한”인지는 이 발췌에 정의되어 있지 않습니다.

비정상 값이 실제 제한을 우회하는지는 사용처를 확인해야 하지만, **설정 상수 자체가 비정상 숫자를 허용하는 문제는 확인됩니다.**

**수정 필요 내역**

- 모든 숫자 설정에 `Number.isFinite()`와 범위 검증을 적용합니다.
- 토큰 한도는 정수로 제한합니다.
- 잘못된 설정은 조용히 보정하지 말고 시작 실패 또는 자동 처리 보류로 처리합니다.
- 0의 의미와 최대 허용값을 명시합니다.
- 추정 비용은 실제 청구액의 확정 상한이 아님을 구분해 표시합니다.

### 7) [P2] 상품 트랙 정규식에 공백 표현 오기가 있음

**근거: 119줄**

`판매s*페이지|상품s*페이지`는 공백이 아니라 문자 `s`의 반복을 의미합니다. 공백이 포함된 “판매 페이지”, “상품 페이지”를 의도대로 분류하지 못할 수 있습니다.

**수정 필요 내역**

```js
/(시장|경쟁사|리서치|설문|사업계획|판매\s*페이지|상품\s*페이지)/i
```

공백 없는 표현, 한 칸 및 여러 칸 공백이 있는 표현을 각각 검증해야 합니다.

### 8) [P1] 학술 대필 제외와 일반 과제 접수의 경계가 불명확함

**근거: 125줄, 1606줄**

125줄은 학술 대필을 제외하지만, 1606줄은 일반 과제·레포트를 접수한다고 안내합니다. 접수 자체가 곧 부적절한 대필이라는 뜻은 아니지만, 현재 문구는 지원 범위를 명확히 구분하지 않습니다.

**수정 필요 내역**

- 교정·구조 피드백·자료 및 인용 정리·학습 지원 등 허용 범위를 명시합니다.
- 고객이 직접 작성해야 하는 평가물을 대신 완성하는 요청과 보조 작업을 구분합니다.
- 제출처 기준 확인이 필요한 경우 견적 확정 전에 확인하도록 합니다.

## 2. 발췌만으로 확인되지 않은 핵심 안전 게이트

아래 항목은 **미구현 확정 사항이 아니라 추가 코드 확인이 필요한 승인 보류 항목**입니다.

| 분야 | 근거 줄 | 현재 확인 가능한 내용과 필요한 보강 |
|---|---:|---|
| 고용·견적·결제 권한 | 40, 47–50 | 규칙은 프롬프트에 존재합니다. 실행 시 고용 확정, 담당자 견적 승인, 고객 동의, 실제 결제 내역을 서버 상태로 대조하는지 확인해야 합니다. “봤어요”, “나중에”, “결제했어요”만으로 주문·결제를 확정해서는 안 됩니다. |
| 결제·상태 변경 API | 39, 48–50 | 실제 API 라우트는 이번 제공 범위에 없습니다. 인증·주문별 권한·상태 전이 검증·변경 이력·재요청 처리를 확인해야 합니다. |
| Astra 최종검수 | 74, 152–178 | 별도 채점 호출 방침은 있지만, 호출 구현은 없습니다. 165–170줄의 함수도 최종검수 여부·파일 버전·해시·검수 대상 주문을 확인하지 않습니다. 호출부에서 이를 보장하는지 확인해야 합니다. |

**특히 최종검수에서는 채점 입력과 전달 파일의 일치를 확인해야 합니다.** 176줄은 추출·마스킹한 텍스트를 채점 입력으로 사용합니다. 이 코드만으로 실제 파일의 레이아웃·파일 무결성·실행 가능성을 검사했다고 인정할 수 없습니다. 최종 파일에 대한 별도 검사 결과를 연결하고, 채점 이후 파일이 바뀌면 승인을 무효화해야 합니다.

## 3. 적용해야 할 핵심 상태·전달 원칙

다음 조건은 프롬프트 지시뿐 아니라 서버의 실행 조건으로 강제해야 합니다.

1. **고객응대:** 첫 고지와 연락 중단 여부를 대화별로 저장하고, 이미 받은 정보는 다시 묻지 않습니다.
2. **견적:** 범위·형식·분량·납기·금액·버전을 고정하고 담당자 승인과 고객 동의를 구분합니다.
3. **결제:** 주문·거래 ID·금액·실제 결제 상태가 일치할 때만 다음 단계로 이동합니다.
4. **추가금:** 범위 변경 시 작업을 보류하고, 명시적 동의와 필요한 결제 확인 후 재개합니다.
