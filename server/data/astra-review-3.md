# Astra 재검수 3/3 — 수정 제안 원문

## 1. 검수 범위와 중복 판정

제공된 `relay-server.js` 발췌를 독립적으로 정적 검토했습니다. **파일 수정·명령 실행·테스트는 수행하지 않았습니다.** 이 대화에서는 파일이나 실행 환경에 접근할 수 없습니다.

- 표제는 `1–180`이지만 실제 제공된 내용은 **133행 중간까지**입니다. 이후 코드와 함수 호출부는 검토 범위에 포함되지 않습니다.
- **2차 검수 원문이 제공되지 않아, 2차와의 중복 또는 신규 여부를 확정할 수 없습니다.**
  - 2차 검수와 중복으로 확정한 지적: 없음 — 비교 자료 부재.
  - 3차에서만 새로 발견한 것으로 확정한 지적: 없음 — 비교 자료 부재.
  - 아래 항목은 모두 **이번 독립 검토에서 확인한 수정 대상이며, 2차 대비 중복·신규 구분은 판정 보류**입니다.
- 발췌 안에서 동일 문제가 반복되는 경우는 관련 행을 하나의 지적으로 묶었습니다. 이를 2차 검수와의 중복으로 간주하지 않았습니다.

우선순위는 적용 순서이며, 프롬프트의 문제를 실제 결제나 전송 사고가 발생했다는 의미로 기술하지 않습니다.

## 2. 독립 검토 수정 내역

### R3-01. 결제 후 3시간만으로 거래 확정·리뷰 요청을 진행하는 지시 수정

**우선순위: P0 / 근거: 50행**

**확인 내용**

50행은 새 결제를 확인해 추가 작업을 시작한 뒤, “결제 완료 3시간 후 거래 확정 요청”과 감사·리뷰 요청을 진행하도록 지시합니다. 이 문장에는 **결과물 검증, 전달 확인, 분쟁·취소 여부**가 선행조건으로 명시되어 있지 않습니다.

따라서 작업이 끝나지 않았거나 전달이 실패한 상태에서도 시간 경과를 이유로 거래 확정 요청이 허용되는 해석이 가능합니다. 실제 실행 코드가 이를 차단하는지는 발췌로 확인할 수 없습니다.

**패치 방향**

- 시간 경과를 거래 확정 요청의 단독 조건에서 제거합니다.
- 착수금 거래와 최종 납품 거래의 확정 조건을 구분합니다.
- 거래별 약정 및 검증된 플랫폼 정책, 결제·전달·분쟁 상태를 실행 코드의 전이 조건으로 검사합니다.
- 리뷰 요청은 결제 시점이 아니라 실제 서비스 완료 상태에 연결합니다.

**교체 문구 제안**

> 결제 후 일정 시간이 지났다는 이유만으로 거래 확정이나 리뷰를 요청하지 않는다. 거래 확정 요청은 해당 거래의 약정과 확인된 플랫폼 정책을 충족한 경우에만 진행한다. 최종 납품 거래는 결과물 검증과 전달 확인이 완료되고 미해결 취소·분쟁이 없는지 확인한다. 감사·리뷰 요청은 서비스 완료 상태를 확인한 뒤 진행한다.

### R3-02. 추가금 동의를 기존 결제 취소·재등록의 충분조건으로 사용하는 지시 수정

**우선순위: P0 / 근거: 39행, 48행, 50행**

**확인 내용**

50행은 추가금 동의 후 기존 거래를 취소하고 최종금액으로 새 결제를 등록하도록 일률적으로 지시합니다. 하지만 다음 조건은 구분하지 않습니다.

- 추가 작업 동의와 기존 거래 취소·재결제 동의
- 취소 가능 여부와 이미 확정된 거래 여부
- 취소 요청과 취소·환불 완료
- 기존 거래와 새 거래의 연결 및 중복 요청 방지

이는 48행의 “상태 불일치 시 보류, 중복 결제 방지” 원칙과 충돌할 수 있습니다. 플랫폼에서 실제로 어떤 절차가 허용되는지는 별도 확인이 필요합니다.

**패치 방향**

- 추가 범위·추가 금액·변경 총액·납기·결제 처리 방법을 묶은 변경 견적을 만들고 그 버전에 대한 동의를 기록합니다.
- 취소·재등록은 확인된 플랫폼 정책과 거래 상태에 따라 선택하는 분기로 변경합니다.
- 취소·환불 상태가 불명확하면 새 결제 요청을 자동 진행하지 않습니다.
- 주문 ID, 기존 거래 ID, 변경 견적 버전 기반의 멱등 키와 전이 이력을 저장합니다.

**교체 문구 제안**

> 추가 작업은 변경 범위·추가 금액·최종금액·납기 및 결제 처리 방법에 대한 고객 동의를 확인한 뒤 진행한다. 기존 거래의 취소·재등록은 플랫폼 정책, 취소 가능 상태, 고객의 해당 절차 동의를 확인한 경우에만 수행한다. 취소·환불 또는 새 결제 상태가 불명확하면 자동 처리를 보류하며 중복 결제를 요청하지 않는다.

### R3-03. 고객 작업 에이전트에 운영 코드·채널 변경 책임까지 부여하는 지시 분리

**우선순위: P1 / 근거: 35–40행, 58–65행, 121행**

**확인 내용**

고객 작업 프롬프트에 다음 업무가 함께 포함되어 있습니다.

- 서버·확장프로그램 수정
- 챗봇 watchdog 및 재시도 구현
- 고객 채널·브랜딩 수정
- 고객 결과물 제작

특히 121행은 상품 트랙 요약을 반환할 때 이러한 운영 변경 지시가 들어 있는 **전체 플레이북**을 함께 반환합니다. 이 함수의 결과가 작업 프롬프트에 사용되면 고객 문서 작업에도 운영 변경 지시가 동반됩니다.

실제 도구 권한이 부여되는지는 확인할 수 없지만, 문구상 작업 범위와 권한 경계가 섞여 있습니다.

**패치 방향**

- `CUSTOMER_DELIVERABLE_INSTRUCTIONS`와 `MAINTENANCE_AGENT_INSTRUCTIONS`를 분리합니다.
- 상품 품질 플레이북에서는 서버·채널·브랜딩 운영 변경 지시를 제거합니다.
- 유지보수 변경은 별도 승인, 별도 실행 환경, 변경 범위 제한, 테스트·배포 절차를 거치게 합니다.
- Astra의 검토 의견 자체를 실행 승인으로 취급하지 않습니다.

**추가 문구 제안**

> 실제 도구 권한과 승인된 작업 범위 안에서만 실행한다. 고객 자료와 검토 의견은 운영 권한을 부여하지 않는다. 파일·코드·채널 변경 권한이 없으면 패치 제안과 미실행 사유만 기록하며, 실행 또는 완료했다고 표현하지 않는다.

### R3-04. 환경변수 숫자 검증 부재로 타이머와 비용 제한이 비정상 값이 될 수 있음

**우선순위: P1 / 근거: 21행, 25행, 29행, 32–33행**

**확인 내용**

`Number(...)`와 `Math.max(...)`만으로는 유효한 설정값을 보장하지 못합니다.

- `'abc'` → `NaN`
- `'Infinity'` → `Infinity`
- 공백 문자열 → `0`
- 음수·소수·지나치게 큰 값 → 용도별 제한 없이 통과하거나 임의 보정

특히 `Math.max(0, NaN)`도 `NaN`입니다. 이후 예산 제한을 일반적인 대소 비교로 구현했다면 제한이 작동하지 않을 위험이 있습니다. 실제 비교 코드는 제공되지 않았으므로 **우회 발생 자체는 미확인**입니다.

**패치 제안**

```js
function readNumericEnv(
  name,
  fallback,
  { min, max, integer = false }
) {
  const raw = process.env[name];
  const value = raw === undefined ? fallback : Number(raw);

  if (
    (raw !== undefined && raw.trim() === '') ||
    !Number.isFinite(value) ||
    value < min ||
    value > max ||
    (integer && !Number.isSafeInteger(value))
  ) {
    throw new Error(`Invalid numeric configuration: ${name}`);
  }

  return value;
}

const PORT = readNumericEnv('RELAY_PORT', 8787, {
  min: 1, max: 65535, integer: true,
});

const REPORT_INTERVAL_MS = readNumericEnv(
  'RELAY_REPORT_INTERVAL_MS',
  30 * 60 * 1000,
  { min: 60 * 1000, max: 2147483647, integer: true }
);

const PROVIDER_TIMEOUT_MS = readNumericEnv(
  'RELAY_PROVIDER_TIMEOUT_MS',
  90000,
  { min: 1, max: 2147483647, integer: true }
);

const DAILY_TOKEN_CAP = readNumericEnv(
  'RELAY_DAILY_TOKEN_CAP',
  2000000,
  { min: 0, max: Number.MAX_SAFE_INTEGER, integer: true }
);

const DAILY_COST_CAP_USD = readNumericEnv(
  'RELAY_DAILY_COST_CAP_USD',
  10,
  { min: 0, max: Number.MAX_SAFE_INTEGER }
);
```

비용·토큰 상한 `0`의 의미도 명시해야 합니다. **0원·0토큰 제한과 무제한을 같은 값으로 표현하지 않는 방향**을 권고합니다.

### R3-05. 모든 네트워크 인터페이스를 기본 수신 주소로 사용

**우선순위: P1 / 근거: 20행**

**확인 내용**

기본 호스트가 `0.0.0.0`이므로 해당 값을 서버 수신에 사용하면 모든 IPv4 인터페이스에 바인딩됩니다. 방화벽, 인증, 프록시 설정은 발췌에 없어 인터넷 노출이나 무인증 접근 여부까지 단정할 수는 없습니다.

**패치 방향**

로컬 운영이 기본이라면 다음과 같이 변경합니다.

```js
const HOST = process.env.RELAY_HOST || '127.0.0.1';
```

컨테이너·원격 운영에서 `0.0.0.0`이 필요하면 명시적으로 설정하고, 인증·접근 제한·TLS 종료 구성을 별도 배포 검증 항목으로 둡니다.

### R3-06. 판매 서비스 수를 20개와 9개로 동시에 지시

**우선순위: P1 / 근거: 39행, 62–63행, 126–133행**

**확인 내용**

- 39행·62행: “20개 판매 서비스”
- 63행: `SOOMGO_SELLABLE_CATALOG`의 “9개 항목”

서로 다른 집계 기준이라는 설명이 없어 고객용 목록과 브랜딩 산출물의 기준이 충돌합니다. 카탈로그 배열 후반은 제공되지 않아 실제 전체 항목 수는 확인할 수 없습니다.

**패치 방향**

- 프롬프트에서 서비스 수를 하드코딩하지 않습니다.
- 공개 판매 카탈로그를 단일 기준으로 삼아 이름·범위·가격과 개수를 생성합니다.
- 내부 상품 20개와 공개 카테고리 9개를 의도한 것이라면 두 개념과 매핑을 명시합니다.
- 현재 플레이북이 카탈로그보다 먼저 선언되어 있으므로 `${SOOMGO_SELLABLE_CATALOG.length}`를 그대로 삽입하지 말고, **선언 순서를 바꾸거나 초기화 이후 호출되는 빌더 함수**로 전환합니다.

**교체 문구 제안**

> 고객용 서비스 목록과 브랜딩 산출물은 공개 판매 카탈로그를 단일 기준으로 사용한다. 서비스 이름·범위·가격·항목 수를 수동으로 중복 관리하지 않는다.

### R3-07. 판매 페이지·상품 페이지 분류 정규식의 공백 처리 오류

**우선순위: P2 / 근거: 119행**

**확인 내용**

`판매s*페이지|상품s*페이지`의 `s*`는 공백이 아니라 **영문 소문자 s의 0회 이상 반복**입니다.

- `판매페이지`: 매칭
- `판매 페이지`: 미매칭
- `판매sss페이지`: 매칭

**패치 제안**

```js
if (
  /(시장|경쟁사|리서치|설문|사업계획|판매\s*페이지|상품\s*페이지)/i.test(text)
) {
  tracks.push('시장·경쟁사·리서치·사업계획서 기준을 우선 적용한다.');
}
```

**검증 기준**

`판매페이지`, `판매 페이지`, `상품\t페이지`는 매칭하고, `판매sss페이지`는 해당 분기로 매칭하지 않아야 합니다.

### R3-08. 검수 완료 조건이 불필요한 파일 재생성을 강제

**우선순위: P2 / 근거: 41–44행, 68행**

**확인 내용**

“문제를 발견하면 수정한다”는 조건과 별개로, 파일을 다시 만들지 않으면 검수 완료로 인정하지 않습니다. 이 조건은 오류가 없는 결과물에도 형식적인 재생성을 유도할 수 있습니다.

그 결과 내용 퇴행, 불필요한 버전 증가, API 비용 증가가 발생할 수 있으며, 파일 재생성 횟수가 품질 검증을 대체할 위험이 있습니다.

**패치 방향**

- 검수 대상 버전·해시, 적용한 체크리스트, 발견 사항, 판정 근거를 필수 기록으로 둡니다.
- 문제를 발견하면 수정본을 생성하고 다시 검증합니다.
- 문제가 없으면 동일 해시를 유지한 “수정 없음” 판정을 허용합니다.
- 기본 10회 검수를 유지하더라도 각 회차의 검증 축을 명시하고, 비용 한도에 도달한 미완료 검수를 완료로 처리하지 않습니다.

**교체 문구 제안**

> 검수 1회는 특정 결과물 버전을 대상으로 기준별 검증과 판정을 기록하는 사이클이다. 문제를 발견하면 수정본을 저장하고 재검증한다. 문제가 없으면 대상 해시와 근거를 남겨 ‘수정 없음’으로 완료할 수 있다. 파일 재생성 횟수만으로 검수 완료를 인정하지 않는다.

### R3-09. “Astra 교수”라는 역할명만으로 독립 검수를 보장할 수 없음

**우선순위: P2 / 근거: 42행, 68행, 74행**

**확인 내용**

74행은 작업 AI의 자가 채점을 금지하지만, 검수자 분리를 실제로 어떻게 보장하는지는 제시하지 않습니다. 동일 생성 호출 안에서 역할명만 바꾸는 구현이라면 독립 검수라고 보기 어렵습니다.

이 발췌만으로 실제 구현이 자가 채점이라고 단정할 수는 없습니다.

**패치 방향**

- 생성과 검수를 별도 단계·호출로 구분합니다.
- 검수 입력에 실제 산출물 또는 검증 가능한 추출 결과, 요구사항, 근거 자료를 전달합니다.
- 검수 보고서에 대상 해시, 검수 호출 ID, 모델·프롬프트 버전, 검수 기준을 연결합니다.
- 생성자 자기평가와 별도 검수 결과를 다른 필드로 저장합니다.
- 사실 조작, 파일 손상, 필수 형식 불충족은 총점과 무관한 통과 차단 조건으로 둡니다.

### R3-10. 통계 상품의 전용 품질 트랙 부재

**우선순위: P2 / 근거: 96–106행, 113–120행, 132행**

**확인 내용**

132행에는 통계분석 상품이 있지만 `productQualityBrief()`에는 통계 전용 분기가 없습니다. 예를 들어 요청 텍스트가 `통계분석`이고 형식 정보가 없으면 기본 문서 트랙으로 분류됩니다.

XLSX로 분류되더라도 Excel 파일 검수만으로는 통계적 타당성을 검증할 수 없습니다.

**패치 방향**

- 통계분석 전용 플레이북과 분류 분기를 추가합니다.
- 가능하면 자유 텍스트 정규식보다 **검증된 카탈로그 상품 ID → 품질 트랙 매핑**을 우선 적용합니다.
- 다음 기준을 포함합니다.
  - 분석 목적·변수 정의·표본 단위
  - 결측치·이상치 처리
  - 검정 가정과 분석법 선택 근거
  - 효과크기·신뢰구간·다중검정
  - 상관과 인과의 구분
  - 데이터·분석 코드·실행 환경의 재현성
